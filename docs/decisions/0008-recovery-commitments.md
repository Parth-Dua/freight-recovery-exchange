# 0008 — Recovery commitments: holds, approval gate, confirmation, lineage (Phase 7, Parth's half)

- **Date:** 2026-10-17 · **Status:** Accepted (user asked for Phase 7; contract additions are optional fields) · **Phase:** 7
- **Contracts (additive, optional fields):** `REQUEST_HOLD.recovery_offer_id` (hold part of a one-shot recovery offer) and `CONFIRM_BOOKING.replaces_booking_id` (lineage). Old messages validate unchanged, but the schema digests change, so the Exchange and the carriers must run the same contracts build.
- **Per-booking offer rows:** a recovery offer can cover several bookings, but `holds.offer_id` and `bookings.offer_id` reference `offers`. The Exchange writes one `offers` row per assignment (`<recovery_offer_id>.<booking_id>`, request = the original booking's request, price = the solver's `unit × units`, status ACCEPTED, carrier's signature from the recovery reply). The carrier holds against it only if it matches its own recovery offer exactly (sailing, container, units, `total // capacity × units`), and caps the units held under one recovery offer at what it offered (row lock on its offer log).
- **Order:** hold every assignment in a fixed order (carrier, sailing, booking) → if any hold fails on attempt 1, release all held legs and run one fresh offer round + solve (attempt 2); on attempt 2 a booking with a failed leg is reported unrecovered → bookings inside their allowance are confirmed; over-allowance bookings keep their hold and go to `ApprovalSeam`, confirmed only on `APPROVED`; `DECLINED`/`EXPIRED`, or a hold that lapses while waiting, releases the hold → confirmed: carrier writes the replacement with `replaces_booking_id`; the Exchange marks the original `SUPERSEDED`, releases its slot claims (WITHDRAWN on a withdrawn sailing) and records `recovery_assignments`.
- **Truthfulness:** only carrier-confirmed legs appear as assignments after PROPOSED. A confirmation with no answer (timeout/unreachable) leaves the run `RECONCILIATION_REQUIRED`; `resume` retries with the same idempotency key. Not globally atomic across carriers: every step is idempotent and recorded per leg in `recovery_legs`.
- **No payment movement:** recovery bookings carry `payment_reference = recovery:<run>` and no Stripe charge or refund (spec 07 §4); the buyer's original claim code hash carries over.
- **Trigger:** `scripts/recovery_worker.py` polls `pending_withdrawals()` and resumes waiting runs. It signs as the Exchange but never reads the mailbox, so it runs beside the Exchange on the same machine.
- **Approval until PR #15 lands:** `build_recovery_seam` uses Tisya's `TigerApprovalSeam` if importable; otherwise over-allowance bookings wait and their holds lapse (never confirmed without approval).
